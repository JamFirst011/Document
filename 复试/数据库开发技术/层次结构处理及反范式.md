# 层次结构处理

最开始的数据库存储结构，就是像树一样的层次结构， 这会使得数据间耦合性很强，缺少灵活性; **层次数据库复杂的主要原因**在于访问数据的方式本质上是访问树的方式，因此需要访问树的全部或部分节点；但是树状结构的数据存储很符合逻辑和直觉；因此本节主要介绍如何为层次数据进行表的设计；

## 处理层次结构

层次结构的表设计有三种模式，他们都满足 3NF: 
1. 邻接模式 : 父节点的 ID 作为子节点的一个属性，这样父子节点就被明确的关联起来。表中一定有当前记录的 ID 和他的 PID
2. 物化路径模型 : 将树中的节点和他在树中的位置的描述数据相结合，例如存储 1.2.3 这样的从根节点到当前节点的路径，他的父亲节点，兄弟节点和子节点都非常清晰
3. 二者的区别 : 邻接模式中，一个节点下面的子节点都是平等的，但是物化路径模型中可以对一个节点的子节点进行排序
3. 嵌套集合模型 : 每个节点被赋予一对数字，一个节点的数字为其子节点的左右两侧的数字; 例如父节点是 0-10，那么他的子节点就是 1-5，6-9; 叶节点的 `rnumber = lnumber + 1`

## 层析结构自顶向下查询

在部队数据库中，查询 Vandamme 指挥哪些部队
1. 邻接模型 : 使用connect by对记录进行连接，只要指定用于连接的字段，例如 `connect by pid = prior id` 即可将所有记录连接为层次结构，接下来只需要指定一个节点，查询就会返回该节点及其所有子节点表示的记录; 若没有connect by，那么只能使用with as进行递归查询; 若没有connect by语句，建议使用后面的模型
2. 物化路径模型 : 只要一次连接，即可以找出所有路径前缀和 Van 将军部队记录的路径相同的记录; **计算层次**: 用path字符串的长度减去将该字符串中的 `.` 去掉后的字符串长度，可以得到点的数量，即为节点所在层次；对记录按照path进行排序即可以得到深度优先遍历的结果；
3. 嵌套集合模型 : 同样只需要一次连接就可以找出目标节点的所有后代，但是排序非常复杂；

**三种查询的性能比较** : 在有connect by，以及需要对结果进行排序使其和深度优先遍历得到的顺序一致时，邻接>物化路径>嵌套集合;
- 邻接模型: connect by性能极强
- 物化路径 : 因为查找和排序都要大量操作字符串因此效率不如邻接模型
- 嵌套集合模型 : 查找后代的速度是最快的，因为只需要一次连接和数字操作，但是排序付出的性能消耗巨大

## 层次结构自底向上查询

**Highland查询** : 找出所有在描述中出现了 `HighLand` 的部队以及他们上面的部队; 自底向上查询有多个出发点，很难使用索引，要做全表扫描因此慢于自顶向 下
1. 邻接模型 : connect by, 此时 connect by 写成 id=priorpid，相当于以自底向上的顺序构建树。但是邻接模型会返回冗余的记录，因为他返回的是所有满足条件的叶节点的到根的路径，所以可能会出现多个节点有一部分相同的路径情况; 如果要结果是以树的形式显示，即从跟节点开始，显示所有到目标叶子节点的路径，会非常困难；
2. 物化路径模型 : 用 like 可以找到所有父节点，并且按照物化路径排序，不会返回冗余数据; 效率很高，并且书写很简单
3. 嵌套集合模型 : 查找父节点非常简单，但是排序非常的麻烦
4. 评估 : 邻接模型因为 connect 还是最快，但是他会返回冗余的数据，并且没法进行排序。这种情况下其实物化路径模型最好，他是最通用最均衡的树状
结构设计方案，尤其是对于 MYSQL 没有 connect by


**注意** : 
- 物化路径模型的主键不应该是物化路径，因为主键应该不变，但是不能确保 节点的位置不变。
- 若将物化路径中的path，设定为每个节点最多只有100个孩子节点，那么路径中就不需要点，例如 000265表示跟节点的第二个孩子的第65个孩子；此时获取节点在树中的位置可以通过直接比较字典序，不需要使用函数；

## 聚合来自树的值(聚集查询):

**对保存于叶节点的值做聚合** :查询 Van 将军统帅的总人数:此时物化路径模型好于邻接模型，因为物化路径模型可以使用到所有的中间值，来得出每个子部队的人数。

**计算某个值散步在树中各层次的百分比** : 此时节点可能有多个父节点，例子如下:

> 药水数据，每种药水由一定百分比的成分组成，成分可以是基础成分，也可以是其他药水；

此时一个基础成分可能有多个父节点，此时如果要计算某药水中某基础成分的百分比，不仅要算该药水中这个成分的百分比，还要计算这个药水中的药水中的该成分百分比，这种查询无法用之前的模型解决。

# 范式和反范式

**范式的优缺点** : 使用的范式越高，创建的表就越多; 会导致对数据操作的性能变低。如果业务经常涉及多个表，并且要求时间尽可能快，这时可以使用反范式

使用反范式会导致数据库规范化的弱化，并进一步导致：
1. 数据库完整性需要手动维持
2. 降低灵活度
3. 提高修改数据库的成本

因此在数据库系统具有低修改性和高查询率时可以使用反范式；

## 反范式

**基于3NF**：首先构建3NF，然后在查询效率过慢时在根据下面的方法弱化规范性；

通过可控制的冗余来提高查询效率，分为以下几种模式:
1. 合并一对一关系 : 如果两个表是一对一的，合并他们会产生很多的 NULL 值， 必须要一个表的记录在另一个表中有足够多的对应才能将他们合并
2. 一对多关系中复制非关键字属性 : 例如有两个表，他们是一对多关系，例如一个表存储了学生信息和学生所在专业编号，而另一张表存储了专业编号和专业信息。如果要频繁的获取学生所处的专业信息，那么就要不断地将两个表连接， 可以考虑将每个学生地一些专业信息复制到学生表中，来加快查询速度，同时要注意对专业信息地更新需要两个表一起更新，可以使用触发器来完成
3. 一对多关系中复制外键 : 典型应用场景就是有三张表 A，B，C，其中 AB 有 相同地列，BC 有相同地列，并且ABC之间都是一对多的关系(即A对应多个B，一个B对应多个C), 此时如果要访问 AC 的内容，就必须用 AB 连接再连接 C 才行; 此时可以将 A 的主键复制到 C 中作为 C 的外键，这样 AC 可以直接连接，减少了连接次数提升了查询效率
4. 多对多关系中复制属性 : 和第二种本质上是一样的。此时不是直接多对多的 两个关系中进行属性复制，而是例如 A 一对多 B，C 一对多 B，此时 A 和 C 是多对多的，此时在 B 中复制 A 或 C 的一些属性可以减少查询次数，本质上是第二种方法的一种衍生；
5. 引入重复组 : 例如一个人有多个电话号，此时符合范式的做法是单独建一张表存储一个人的多个电话号码，在需要时连接查询。而如果引入重复组，则有两种方法
    - 直接将这多个电话号码存储在用户表中，此时必须知道电话号码数量的绝对上限，并且该上限是静态不变的，并且该上限还不能很大，这种方法有很多局限性;
    - 用户表中存储一个缺省值，而其他的所有值单独建立一个表查询，一般查询只用获得一个缺省值就可以了，如果要获得所有值再进行连接; 好处是非常平衡，既有一 定的灵活性还能提升查询效率。
6. 创建提取表 : 什么查询慢，就把什么查询需要的连接组成大表存储下来。非常有效，但是会带来很大的复杂性，并且提取表不能进行计算和更改。
7. 分区表 : 首先必须把数据库设计成满足 3NF 才能考虑打破范式;所有打破范式都会带来 更新的复杂度，并且需要小心控制数据的完整性和一致性。
