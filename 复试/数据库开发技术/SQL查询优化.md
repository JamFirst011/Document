# 关系代数

**定义** : 基于关系表和关系运算的表达式的等价变换。对于一条 SQL 语句，数据库都通过查询优化器将他转换为代价最小的关系表达式。 常用关系运算符如下:
- 投影:选取关系中的一些列，即 $\Pi_{name}$
- 选择:选取关系中的一些元组/记录，即 $\sigma_\theta$
- 笛卡尔积:X
- 连接:相当于对笛卡尔积做选择运算，$\bowtie_{A \theta B}$ 表示按照 theta 所示规则进行连接。
- 外连接:左外连接表示保留左边关系表的所有元组。

# 查询优化器

**作用** : 借助关系理论，对原始查询进行有效的等价变换。优化器分类如下:
- RBO : 基于规则的优化器, 匹配关系代数局部结构并进行替换，而具体规则, 例如如何匹配，匹配的优先级需要人工设置，通用性较低
- CBO : 基于成本的优化器, 不断应用不同规则生成不同的关系代数表示，并估算每种的成本，即可进行优化。具体为首先计算全表扫描的成本，然后找出所有可用的索引，计算使用不同索引的代价并对比，找到最优路径

**查询优化器的流程** : 首先语义语法检查，随后解析并生成多个解析树，选择最好的解析树， 生成二进制执行计划，并将其抛入执行引擎，执行引擎访问数据库进行执行。

**优化器的特性** : 优化是在查询真正要被执行时发生的;有相同结果，但是写法不同的关系表达式执行效率可能有很大不同;
- 优化器只能对独立查询进行优化
- 优化器在一定时间内遍历查询的最优方式
- 一个独立查询效果可能很好，但是他把嵌入一个更复杂的查询内部优化效果可能变差，因为没有足够时间遍历所有的查询方式
- 查询中的非关系部分很难优化, 例如order by
- 数据约束的语义信息在声明中体现，这样优化器可以根据这些信息进行优化


# 使用 SQL 需要考虑的因素:

1. 获得结果集需要访问的数据量(最重要因素) : 首先要确定目标数据容量然后才能考虑执行效率
2. 定义结果集需要的查询条件 : 从初始的表，到查询结果之间的发生的变化就是查询条件(即where子句)，过滤条件有效率的高低，也就是如果一个查询条件能够剔除更多的数据，也就是满足该过滤条件的记录数更少，那么这个过滤条件效率就更高
3. 结果集的大小 : 查询返回的数据量，取决于表的大小和过滤条件的细节。单纯的考虑结果集大小是不对的，应该使得响应时间和返回的记录数成正比, 提高用户满意度即可
4. 获得结果集需要涉及的表的数量 : 多表连接会使优化时间成指数级增长，如果要多表优化应该首先质疑表设计的合理性
5. 同时修改这些数据的用户的多少 : 考虑并发性，即所有用户的整体吞吐量

# 其他方面

## 过滤条件

即where子句和having子句，主要分为以下两种过滤条件：
1. join过滤条件： 用于连接表
2. select过滤条件：直接作用于select子句

**过滤条件的顺序**：在对SQL查询没有性能影响时，过滤条件的顺序无所谓；否则：
- 更高效的过滤条件应该先执行，使得中间结果更小；
- 要根据实际情况考虑，来选择先执行更高效的过滤

**子查询**：子查询可以分辨过滤条件的好坏(即将不同的过滤条件放到子查询中先执行，随后用得到的结果再去执行其他过滤条件；来得到过滤条件的不同执行顺序得到的性能；), 以及消除distinct(即子查询一般跟在in/exist后面，子查询中的distinct此时对结果没有影响，可以直接消除distinct)；如果没有这两个需求，最好不要使用子查询，因为优化器很难对子查询进行优化；
