# 观察者模式

建立一种对象之间的依赖关系，当一个对象(观察目标)发生变化时，很多观察者对象也自动发生变化；观察者之间没有关系，可以方便的添加观察者，包含以下角色：
- Subject
- ConcreteSubject
- Observer
- ConcreteObserver

其中Subject中定义了订阅他的观察者列表，以及添加/删除观察者的接口，Observer中定义了update接口；在客户端，首先创建观察目标对象，随后为观察目标关联多个观察者，并调用观察目标的notify，目标就会通知所有的观察者，也就是调用他们的update

### Analyse

- **优点**：
    1. 实现表示层和数据逻辑层的分离
    2. 符合OCP
- **缺点**：如果有多个观察者，那么系统会很复杂并且难以维护；将所有观察者都通知到需要花费很多时间；观察者状态变化可能引发进一步通知等；
- **适用情况**： 系统中有两个方面，一个方面依赖另外一个，一个对象的改变将引发多个对象的改变

MVC是观察者模式的扩展，其中Model为观察目标，V是观察者，当数据发生变化时，视图自动更新

# 中介者模式

当系统中对象职责不清晰，对象之间耦合度很高，相互引用很多，导致对象复用较差，且更改较为复杂时可以使用中介者模式,来主要降低对象之间的耦合，由以下部分组成：
- Mediator
- ConcreteMediator
- Colleague
- ConcreteColleague

中介者有两方面作用，在结构上，可以让同事对象之间不再互相引用，中介者包含对所有同事的引用，而同事只需要包含对中介者的引用即可；在行为上，中介者对同事之间的交互进行封装，可以对同事的请求做进一步处理；注意这里的交互指的不是调用某个同事的某中方法，而是向观察着那样，某个同事执行某个行为后其他同事都可以观测到这个行为，这个行为必须要通过中介者来实现，例如聊天室

### Analyse

- **优点**：降低耦合，集中控制
- **缺点**：中介者可能过于庞大，可读性降低

中介者对象就像是MVC中的Controller，同时，中介者模式使得对象中的引用减少到最小，是迪米特法则的典型应用； 

# 模版方法模式

基于继承的代码复用技术，将共同的逻辑放在父类中，将不同的方法实现放在不同的子类中；具体是：在父类中定义一个操作中算法的骨架(模版方法,把基本方法/步骤组合在一起的总方法)，而步骤的具体实现则放在子类中，使得子类可以在只更改一些步骤的情况下改变这个操作；

### Analyse

- **优点**： 更加符合单一职责原则，更好的代码复用
- **缺点**： 每个不同算法都要定义一个子类，使得类数量大量增加

**钩子方法**：在基类中的方法，一般有默认定义，子类可以选择重写；在模版方法中，钩子方法通常返回一个bool值来决定某个步骤是否要执行，而子类可以改变这个钩子方法来改变模版方法中的步骤执行过程，实现子类对基类的反向控制
