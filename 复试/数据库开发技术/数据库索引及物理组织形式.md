# 索引

**基本概念**: 索引是方便查询的，有两种索引类型，顺序和散列，其中散列索引将值分到若干桶中，分到哪个桶是由散列函数决定的。可以根据访问类型，访问时间，插入删除时间和空间开销来评估索引好坏。用于搜索元组的属性称为搜索码。索引适用性的依据是检索比例，也就是一次查询中使用索引可以加速的部分,该部分占比越高，索引就越好用。

**使用索引一定会加快查询速度嘛**：不一定，用B+树索引举例，能否加快查询速度取决于：
1. 表的大小
2. 查询结果的数据量，例如 `select *`

因此索引不一定会加快查询速度，他是一种细粒度直接读取记录的技术，而不是为了检索大量数据而存在的技术；

**如何判断索引有用**：根据检索比例判断，检索比例指通常情况下检索到的数据占总数据的百分比，若在10%以下，那么认为索引有用；(实际情况中，要根据表的情况来确定这个检索比例)

**可以使用B+树索引的两个情况**：
1. 只需要检索很少的行
2. 需要检索很多的行，但是可以只使用索引不使用表(使用复合索引，例如对属性x，y构建索引，并且查询的结果只包含x，y属性)

## 顺序索引(按搜索码顺序存储索引):

**聚集索引/主索引**: 其搜索码定义了文件的顺序，而非聚集索引/辅助索引:搜索码指定的次序和文件的排列顺序不同。有聚集索引的文件被称为索引顺序文件。

**稠密索引和稀疏索引**: 
1. 稠密索引：首先索引项包含一个搜索码值和指针。稠密索引对每一个搜索码的值都有一个索引项，如果是稠密聚集索引，指针指向具有该搜索码值的第一个记录; 如果是稠密非聚集索引，需要指向所有有该搜索码值的记录; 
2. 稀疏索引: 只为一部分搜索码值建立索引项，并且一定是聚集索引，使用稀疏索引，我们要找到有最大的小于目标搜索码值的索引项，找到其对应记录并一条条往下读就能很快找到。稠密索引更快但是消耗空间更多。一 般使用稀疏索引，为每个页建立一个索引项。

**多级索引**: 就是文件太大为每个记录建立一个索引的话，索引太大只能存在硬盘中，读取耗时高。可以为索引再建立一个索引，因为索引一定是顺序的， 所以可以为索引建立稀疏索引并存在内存中，这样读取速度就可以大大增加

**索引更新**: 插入操作如下
- 稠密聚集索引: 把记录插入到相应位置上，如果他是惟一的就给他加个索引; 
- 稠密非聚集索引: 把记录插入，如果有相同的搜索码值，就把这个搜索码值对应的索引加一个指针，否则加一个索引，大概就是这样很好理解，具体见 p333-334

**辅助索引**: 为非主键建立的索引; 因为记录在物理上是按照主键进行排序的，因此非主键此时一定是非聚集的，所以辅助索引只能为稠密索引; 他一般会带来很大的开销，所以要好好选择在哪个非主码上建立辅助索引

**多码索引**: 索引上的搜索码包含多个属性，称为复合搜索码，索引项按照搜索码值的字典序进行排序。

## B+树索引:

**B+树的定义**: 内部节点的子节点数在特定区间( $\frac{n}{2} - n$ ), 叶节点包含了全部关键字，叶节点之间相互连接

**B+树的结构** : 首先设定参数 n，每个节点都至少包含 $\lceil \frac{n}{2} \rceil$。有两种节点：
- 内部节点：关键字数量最多有n-1个，子树的数量和关键字的数量一致
- 叶子节点：关键字数量范围和内部节点一致，每个关键字对应一个指针指向记录位置，最后一个指针指向下一个叶子节点；

**B+树的查询** : 对于范围查询，其原理为先找到范围左端搜索码值对应的叶节点，然后一点点往右读，并将指针加入到结果集中，直到读到范围右端。查询的代价很小，因为每个节点都很大所以树很矮，假设共有 N 个搜索码值，那么查询代价为 $\lceil log_{\lceil \frac{n}{2} \rceil}N \rceil$ 。 如果有用于解决非唯一搜索码的多码查询，那么就相当于一次范围查询。

c. B+树的更新:主要是插入和删除操作，并且主要就是考虑节点的拆分和合
并。插入见 p343。删除见 p346，更复杂一点。

**现实中B+树的插入** : 
- 乐观插入: 就是不改变树结构的插入，即如果叶节点中有足够空间则直接插入
- 悲观插入: 即判断分裂点，创建新页面，并改变树结构; 页面分裂有一定的优化策略:其实就是尽可能在原页面中间分裂;
- 删除时也是同样，先进行乐观删除然后悲观删除。

**B+树更新的复杂度** : 插入的复杂度和查询复杂度成正比; 以下为解决非唯一化搜索码的方法：
- 唯一化属性: 要构造唯一性搜索码，需要的额外的属性称为唯一化属性; 
- 桶 : 一个搜索码值对应一个索引项，但是索引项的指针指向一个桶，桶中存储了所有具有该搜索码值得记录，这种方法会对删除带来非常大的开销; 
- 直接将多个对应相同搜索码值的索引项存到树中，同样也会造成非常大的删除开销。所以一般都使用惟一化属性使得搜索码值惟一。

**B+树的优缺点:**
1. 优点 : 全键值查询，查询具有某一特定值的记录很快，还有适度的范围查询，以及前缀查找。
2. 缺点 : 不能做到前缀匹配查询(即前缀用通配符代替，只知道后缀的查询，例如查询 like ‘%abc’的字符串), 还不擅长多表连接查询

## 散列索引

**定义** : 维护多个桶(一个桶中包含的是散列函数值相同的搜索码)，每个桶中存储一些记录的指针(或者记录本身)，使用散列函数来为特定的搜索码值定位桶。不管是查询，插入还是删除，都调用散列函数找到记录所在的桶并进行操作即可。

**特点**：
1. 只能进行全键值查询
2. 只能支持=，in等运算符
3. 不支持对字段排序
4. 不能进行范围查询
5. 读取效率相比于B+树索引更高

**如何处理桶满了问题**：
- 溢出链: 也称为闭寻址。当一个桶满的时候，就为这个桶加一个溢出桶，在搜索某个桶内的记录的时候，也必须要搜索他的溢出桶。这种提前规划好桶的数量，在溢出时添加溢出桶的方法称为静态散列。如果有大量相同的搜索码值，或者散列函数设置不合理使得记录并不分散，就可能出现很多溢出桶降低效率，所以可以使用
- 动态散列 : 就是在负载因子(数据和桶的比值)太大的时候重建索引(扩大哈希表，重新设置散列函数并重新计算所有索引)，这可能导致任务中断，所以用增量的方式来改变桶数量，例如线性散列和可扩展散列。

## 函数索引

**适用情况**：
- 查询条件为x的函数: 对 f(x)建立索引，例如不区分大小写的字符串查询，就要先用函数将字符串转为大写，然后对大写字符串建立索引。 
- **属性某种取值占比很大** : 例如某个属性在99%的记录上都取A，那么对A的查询可以不使用索引，也就是对A直接返回 NULL，对B建立一些索引。

## 位图索引

**定义** : 为多码上的简单查询设计的一种特殊类型索引。首先记录必须可以被编号，对于建立了位图索引的属性，对于属性的每一个取值都有一个位数组， 其中第 i 位为 1 当且仅当第 i 个记录在该属性上取该属性值。只能在属性值不多的情况下使用，并且对于单码搜索提升不大，但是对于多码搜索有很大的提升。 对于多个码，只要找到他们位图索引的 and，其对应的位置即是目标记录的编号。

**问题**：在修改带有索引的属性时，或插入新元素时，因为要更新位图索引，必须锁住整个表，降低并发行；

## 位图联结索引

依据另外一张表的某个属性在表上建立位图索引，可以在只访问一个表的情况下进行连接，提高连接效率；例如，员工表存储了员工信息和部门编号，部分表存储了部分信息和部分编号，此时可以在员工表上建立部分编号的位图索引，在大部分查询中都要查询某个部门的员工信息；根据该位图所以可以直接选取对应部分的所有员工而不用进行连接；

## 索引使用的经典问题:

**函数和类型转化对索引的影响** : 
1. 使用函数可能使索引失效，因为索引不知道函数的功能。例如找寻所有x,使得 f(x)=1。此时就无法使用索引
2. 索引和外键:系统的为表上的外键添加索引，可以减少上锁的时间(即在删除主键时，快速查找参照表中有没有对应的外键，若有的话需要停止删除或联结删除); 但是在被参照表为字典表(即不会频繁修改的表)时，不需要为外键构建索引；

**系统生成键**：使用系统提供的自增主键时，当多个事务要插入多个记录时，因为他们的主键是自增的，因为这些记录的索引项位于一个快中，使得对索引的修改变得串行化，降低并发性；
- 解决方法：反向键索引，即一种函数索引，对每个主键id，返回他的反向值，例如9527返回7259；这时连续的主键id就被分配到了不连续的索引快中；

**查询没有使用索引的情况** :
1. 为一个复合搜索码建立 B+树索引，但是在谓词中没有使用复合搜索码最前面的属性，例如为(A，B)建立索引，但是要找所有 B 满足一定条件的记录
2. 使用聚集函数时，优化器可能不会使用索引, 因为要排除null值，例如count(*)大概率会进行全表扫描；
3. 对有索引的列做出函数查询
4. 隐形类型转换：例如将字符串和数字比较时, 此时用数字作为key，无法查询到正确记录；
4. 如果使用了索引会更慢时
5. 没有正确统计信息，使得查询优化器的做出了错误判断，例如存储的表的大小没有更新，导致优化器以为表很小而没有使用索引；

**多码访问** :
1. 使用多个单码索引:如果我们要查找多个特定搜索码值对应的记录，并且每个搜素码上都有索引，那么最有效的方法时，用每个索引找到合适的记录指针，并求他们的交集即可。但是有一个问题，就是如果每个索引都找到很多记录，但是最终的交集只有一小部分，这样就会严重浪费时间，所以就有了位图索引。
2. 多码索引 : 可以用B+树高效处理多码索引。具体就是建立对应于多码的复合搜索码，来进行范围查询
3. 覆盖索引 : 存储了一些额外的，和搜索码没关系的属性，通过这些属性可以在不访问记录的情况下回答查询。例如我们为 ID 建立覆盖索引，每个索引项的值包括了 ID 的值和年龄值，那我们就可以直接回答对于特定 ID 人的年龄查询不需要访问记录(实际上就是在索引项中存储多于查询需要的属性信息)。相比于多码索引，他的索引项更短(因为额外属性存储在索引项中)，所以使得 B+树有更高的扇出，效率更高。

## 索引的创建:
a. SQL 中创建索引的语法:create index name on relation attributions
b. 索引的好处:一般都会自动在主码上建立索引，这样在插入时可以使用索引快速检查主码是否重复。在外码上建立索引也可以很快的进行连接操作

# B 树结构的物理实现(三种变长记录存储方法，五种文件组织形式)

大端序:文件的尾在大端; 小端序:文件的尾在小端

**基本存储逻辑**：按页大小进行存储，不同页之间按照链表方式进行连接；分为目录页和数据页，目录页包含数据页的地址；而数据页包含具体记录；每个页都包含块头(元信息)，页目录(相当于一个稀疏索引，用来更快根据主键查找记录)和存储的各条记录；因为记录被更新时有可能变化，因此出现了**行迁移**,即记录变大后无法在页内存储，将其迁移到新的一页，并在原来位置保留指向新位置的指针，使得索引不用改变；但是会增加查询时的IO次数；因此当页存储满70%时就认为页满了，不再插入新记录，从而减少行迁移；

- 定长记录:每个块中只会存储最大整数个记录，并且在删除某个记录后，直
接将最后的记录移到被删除的位置。但是因为插入比删除更频繁，所以更好 的做法是标记是删除的文件位置，等之后有插入之后直接插入到这个位置。 这时候就需要新的结构:
- 变长记录(三种存储方式):因为有变长域的出现，例如字符串，所以有了变长记录，还有文件中可能有多种记录。要实现变长记录必须解决如下的问题: 
    1. 如何表示单个记录，使得记录中的属性可以被获取，即便他们都是变长 
    2. 如何在一个块中存储变长记录使他们能被提取 
- 一个变长记录头部是一个定长信息的初始部分，其结构对于相同关系的所有记录都是一样的，包含了每个变长属性的偏移量和长度。还会有空位图， 他表示哪个属性为空，哪个属性为空他的第几位就为1。接下来介绍如何在 块中存储变长记录:

**文件头** : 存储第一个被删除记录的位置，而这个位置存储下一个被删除记录的位置，形成一个链表，称为自由链表。在插入时只要找到文件头 中记录的位置插入即可，并将下一个可插入位置赋值给文件头，如果文 件头为空那么子节插到最后面。

**使用记录头存储元数据** : 记录头存储记录长度，第二个变长属性的偏离量，因为第一个变长属性一定在最后一个定长记录后面。

**溢出页** : 将变长数据存储到溢出页中，这样相当于把变长记录变成定长记录。

**分槽的页结构** : 在一个块中，有三个结构，块头，自由空间和记录。块头中包含了记录的数量，指向自由空间末尾的指针，以及每个记录的偏移量，每次要插入记录时，就在自由空间的末尾给他分配空间，并移动自由空间的末尾的指针; 要删除记录时，块中位于该记录后面的记录都被向前移动，自由空间的末尾指针改变。
- 大对象存储 : 数据库常常要存储比块大的记录，例如图片或者音频，大对象可以以文件形式存储在被数据库管理的一个文件系统区域中，或作为文件结构存储在数据库中，此时包含大对象的属性值就为一个指针。但是如果要经常进行数据库备份，那么这个备份就会很大，浪费空间。所以一般把大对象存储在数据库外部，包含大对象的属性值为该大对象的路径。

**文件中记录的组织** : 关系是记录的集合，如何在文件中组织这个集合, 有堆文件，顺序文件组织，多表聚簇文件组织，B+树文件组织，散列文件组织；
1. 堆文件组织 : 记录随便存储，在插入记录时，可以插入到文件末尾，但是更好的方法是跟踪文件中所有自由空间的位置，并将记录插入自由空间。通过自由空间图来跟踪。这是一个数组，每个元素占一子节，表示一个块中的自由空间所占的比例。在插入先查这个图，找到合适的块并插入，如果没有合适的就分配一个新块。可以建立二级自由空间图，高级空间图中用一个元素来表示 100 个初始自由空间图的元素中的最大值，先查高级图找到一组合适的快，然后再在这些快中进行查找；这样可以有效减少搜索时间。
2. 顺序文件组织:按照某个搜索码的值顺序存储，每个记录包含下一个记录的位置。在插入时，如果要插入位置的后面是一个自由空间，那就把记录插到这，否则将记录插入溢出块中, 并改变前面元素的指针，使得记录在逻辑上保持有序; 在溢出快较少时，物理有序被稍微破坏但是问题不大；但是如果多的话，搜索码顺序和物理顺序的相似性完全消失，此时要对整个文件进行重组。
3. 多表聚簇文件组织 : 在一个块中存储多个表的记录，设定多个关系的相同属性为聚簇码，根据聚簇码来存储，例如 A 的聚簇码为 1 的记录和 B 的聚簇 码为 1 的记录存储在一起，这样在通过聚簇码连接 A 和 B 时就会更加高效， 但是此时对其他类型的查询速度会有严重影响。
4. B+树文件组织:每个节点对应一个块，内部节点中存储节点类型，记录数量，以及到子节点的指针;而叶子节点则存储记录的位置，也就是基址和偏移量。
    - 右侧追加:自增数值作为主索引时，可以将所有加入的记录直接插入索引的末尾，也就是最右侧的叶子，在插满之后不分裂，而是直接分配新的叶子节点。这种特征可以通过批量加载在非自增的主索引中应用
    - 划分:可以将关系中的记录划分为更小的关系，这些关系基于一个属性分别进行存储，这样对某些特殊查询会有很大的性能提升

**数据字典存储** : 上述为关系的存储，而数据库还要存储关于关系的模式，即元数据，其存储在数据字典/系统目录的结构中，系统必须存储: 关系的名称, 关系中属性的名称, 属性的域和长度, 数据库上定义的视图的名称，视图的定义, 完整性约束, 用户名称，密码以及其他信息, 每个用户的授权信息, 关系中元组的数量, 包含每个关系的文件名称等; 所有这些元数据构成了一个微型数据库，但是一般也可以直接用关系表来存储这些元数据，并将这些关系表放在固定位置，

**对文件系统的维护** : 维持完整性和有序等; 可以通过将记录删除后填为 NULL 或者删除偏移量来消除更新和删除碎片；

## 数据库缓冲区

缓冲区就是主存中用来存储数据库拷贝的那部分，尽量增加需要数据在缓冲区的概率可以有效提升性能。负责缓冲区分配的子系统称为缓冲区管理器

**缓冲区管理器** : 需要数据时向缓冲区管理器发请求，如果缓冲区有就返回，否则就移除某些缓冲区数据，然后将需要的数据读入缓冲区并返回。
1. 缓冲区替换策略:移出块的策略，理想情况下移出未来最长时间不会被使用的块，但是没法预测未来;并且如果没有选择合适的替换算法，单纯增加缓冲区大小没法提高效率
2. 被钉住的块:在某些进程对缓冲区的某个块进行读取或写入时该块不能被移出，因此进程在读写快时要将其钉住，结束操作后解除钉住，没有被钉住的块才能被移出，可以通过为每个块维护钉住计数来实现这个功能。
3. 缓冲区上的共享排他锁:就是你后面看到的共享排他锁
4. 块写出:对块进行写出的时间有限制，不能太久不写出，要写出块必须获得该块的共享锁，也就是写的时候可以读，注意，写出不是移出
5. 块的强制写出:例如在崩溃时将块强制写出

**缓冲区替换策略** : 例如 LRU 策略，还有立即丢弃策略，就是用完就丢掉。 一般还是使用LRU
1. LRU : 最近最少使用
2. FIFO : 先进先出
3. 2Q的LRU : 维护两个队列，一个热队列一个冷队列，开始时将页移入冷队列，该页被使用后移如热队列。哪个队列满了就移出一些哪个队列的页面。可以有效解决普通 LRU 的缓存抖动问题。问题就是实现比较复 杂，并且要设定好两个队列的长度才能最大化性能
4. LRU-K : 为每个页面存储 K 次最近访问时间，在进行替换时会考虑 K 次 访问时间，移出 K 次最远的页面。可以有效提高缓冲命中率，但是实现复杂，耗费空间。
5. CLOCK : 一种近似 LRU，为每个页面维护一个引用位，在页面被引用后 该位变为 1。如果要替换一个页，那么循环遍历引用位，如果引用位为 1，则将其变为 0;如果为 0 就直接替换。优点是实现简单，可以有效缓 解缓冲抖动，但是其本质还是 LRU，在数据库负载很重时，最近使用时 间并不具有参考性
6. LFU : 关注页面的使用频率，换出最不常用的页面。
7. TinyLFU : 是一种近似 LFU，用三个队列和一个过滤器组成。首先，被移入缓存的进入 admission 队列，这个队列使用 LRU 算法，为每个页维护一个计数器来表示他的访问次数，并不时用过滤器选择访问次数较低的页进入 probation 观测队列。其中的页面如果长时间没有被访问则会被移出，否则则会进入 protected 队列。其中的队列暂时不会被移出，但是如果长时间不被使用又会被移入 probation 队列。相当于根据频率选择保留哪些队列。

**写操作的重排序和恢复** : 可以在内存中进行写操作，并在之后将变化写入磁盘，但是这个顺序和内存中写的顺序可能不同。这在崩溃时可能导致不一致， 一般用一个专门的磁盘，称为日志磁盘来按照执行顺序存储写操作的日志; 如果在对磁盘写操作前崩溃，那么重启后访问日志磁盘并完成未完成的磁盘写。

## 数据自动分组:分区，分表，分库

**分区** : 其实就是将表的数据分摊到不同的硬盘中，优点有:
1. 分区可以存储更多数据
2. 数据管理更加方便
3. 可以通过分区对数据进行精确定位，不需要查询全表数据 
4. 可以跨多个分区磁盘查询，提高吞吐量
5. 在涉及聚合数据查询时可以很容易的进行数据合并 有如下分类:

**水平分区** : 对表的行进行分区，可以根据某个属性进行分区，例如每条记录包含一个年份属性，可以将每年的记录都放到不同的分区中

**垂直分区** : 对列进行分区，每个分区中存储指定列的所有行

有如下的物理实现机制:
**循环分区** : 分区定义为磁盘的存储区域，在插入时按照一定的顺序，循环选择分区，使得不同分区上的数据量大小相似；例如，将一个表放到三个分区中，每次向表中插入记录时，都依次选择第123个分区插入；

**数据驱动分区** : 不像循环分区，各个分区的记录没有关系；数据驱动分区此时选择一个**分区键**，根据这个键的值，来决定记录要放到哪个分区中；有如下实现方式：
- 哈希分区：根据记录分区键的哈希值进行分区；可以通过分区键值快速找到记录的位置，但是无法进行范围查询，每个分区内部记录的相似性较低，更偏向于循环分区；
- 范围分区：根据连续数据的范围对数据进行分区；
- 列表分区：此时分区键只能选择一个属性，每个分区对应分区键的几个值，例如将记录按照地区进行分区，将北京，东北设置为北方分区，将上海等设置为南方分区等；并且设置一个default分区，存储所有分区键值不在设定的列表中的记录；

**分区的优点**：
1. 提高查询性能，特别是查询只涉及某个分区的时候
2. 数据维护简化，更容易针对某个分区进行备份或者索引重新构建
3. 更有效的管理空间
4. 提高并发性
5. 更好的维护大型表

**分区的问题** :
1. 增加数据库的复杂性，提升维护的难度
2. 某些时候可能会性能下降，例如查询涉及多个分区时
3. 分区键如果选择不当可能会导致不均匀的数据分布。只有当数据按分区键均匀分布时收益最大
4. 使用数据驱动分区时，对查询有利，因为他将相似的数据集中在一起，但是会降低插入的并发行，同样也是因为将相似的数据集中在一起导致的；

**什么时候考虑使用分区** : 表的查询速度极慢，只需要使用一部分记录，表中的数据是分段的，数据量大的时候

**分表** : 将一个表分成具有多个具有独立存储空间的实体表。使用分表的时机和分区同样，但是在频繁插入或者联合查询的时候进行分表，主要用于解决访问太大, 并发不够的问题。可以使得单表的并发能力提高，磁盘 IO 性能提高，读写锁影响的数据变少，插入数据库要重新建立的索引的数据变少。
**分库** : 应该就是把数据库中的数据存到不同库中; 当单台 DB 的查询速度不够，或者查询量太多。分库可以突破单节点数据库服务器的 IO 能力限制，解决数据库扩展性问题。分库可以分为
- 垂直分库 : 将不存在关联关系或者不需要 join 的表分库;
- 按照业务垂直分库，例如可以分为资金，会员等多个数据库;
- 水平分库 : 需要解决跨越数据库的事务和连接问题;水平分库;
- 读写分离 : 对于时效性不高的数据，可以读写分离

单机数据库的瓶颈 : 单个表数据量过大，库数据量过大，读写速度遇到瓶颈

**区别和联系** : 都是减少数据库的负担，提高查询和增删的效率，访问量大并且数据多时都可以使用，访问量不大时一般只能用分区。并且分表可以多库，但是分区不行。
