# 观察者模式

建立一种对象之间的依赖关系，当一个对象(观察目标)发生变化时，很多观察者对象也自动发生变化；观察者之间没有关系，可以方便的添加观察者，包含以下角色：
- Subject
- ConcreteSubject
- Observer
- ConcreteObserver

其中Subject中定义了订阅他的观察者列表，以及添加/删除观察者的接口，Observer中定义了update接口；在客户端，首先创建观察目标对象，随后为观察目标关联多个观察者，并调用观察目标的notify，目标就会通知所有的观察者，也就是调用他们的update

### Analyse

- **优点**：
    1. 实现表示层和数据逻辑层的分离
    2. 符合OCP
- **缺点**：如果有多个观察者，那么系统会很复杂并且难以维护；将所有观察者都通知到需要花费很多时间；观察者状态变化可能引发进一步通知等；
- **适用情况**： 系统中有两个方面，一个方面依赖另外一个，一个对象的改变将引发多个对象的改变

MVC是观察者模式的扩展，其中Model为观察目标，V是观察者，当数据发生变化时，视图自动更新

# 中介者模式

当系统中对象职责不清晰，对象之间耦合度很高，相互引用很多，导致对象复用较差，且更改较为复杂时可以使用中介者模式,来主要降低对象之间的耦合，由以下部分组成：
- Mediator
- ConcreteMediator
- Colleague
- ConcreteColleague

中介者有两方面作用，在结构上，可以让同事对象之间不再互相引用，中介者包含对所有同事的引用，而同事只需要包含对中介者的引用即可；在行为上，中介者对同事之间的交互进行封装，可以对同事的请求做进一步处理；注意这里的交互指的不是调用某个同事的某中方法，而是向观察着那样，某个同事执行某个行为后其他同事都可以观测到这个行为，这个行为必须要通过中介者来实现，例如聊天室

### Analyse

- **优点**：降低耦合，集中控制
- **缺点**：中介者可能过于庞大，可读性降低

中介者对象就像是MVC中的Controller，同时，中介者模式使得对象中的引用减少到最小，是迪米特法则的典型应用； 

# 模版方法模式

基于继承的代码复用技术，将共同的逻辑放在父类中，将不同的方法实现放在不同的子类中；具体是：在父类中定义一个操作中算法的骨架(模版方法,把基本方法/步骤组合在一起的总方法)，而步骤的具体实现则放在子类中，使得子类可以在只更改一些步骤的情况下改变这个操作；

### Analyse

- **优点**： 更加符合单一职责原则，更好的代码复用
- **缺点**： 每个不同算法都要定义一个子类，使得类数量大量增加

**钩子方法**：在基类中的方法，一般有默认定义，子类可以选择重写；在模版方法中，钩子方法通常返回一个bool值来决定某个步骤是否要执行，而子类可以改变这个钩子方法来改变模版方法中的步骤执行过程，实现子类对基类的反向控制

# 迭代器模式

通过分离集合的存储和遍历，使得对于不同的集合，client不需要知道集合内部的实现方式，而能够使用统一的方式对其进行遍历；包含
- 迭代器接口
- 具体迭代器
- 聚合接口
- 具体聚合
- client

其中迭代器接口定义了迭代器都要实现的行为，例如next,haveNext，而具体迭代器则根据其对应的具体聚合类型实现这些行为，注意，一般迭代器内部都会包含具体聚合的引用；聚合接口定义了具体聚合需要完成的操作，一般是getIteration返回一个迭代器，而不同的具体聚合则包含列表，以及实现不同的getIteration可能返回不同的，用this来初始化的迭代器；这样client在拿到一个具体聚合时，可以调用这个方法来得到专属迭代器并用迭代器遍历这个聚合

优点是封装遍历逻辑，统一接口，符合OCP，缺点是增加复杂性和性能开销

```java
// 迭代器接口
public interface Iterator<T> {
    boolean hasNext();
    T next();
}

// 聚合接口
public interface BookCollection {
    Iterator<Book> createIterator();
}

// 具体聚合类
public class BookShelf implements BookCollection {
    private List<Book> books;

    public BookShelf() {
        this.books = new ArrayList<>();
    }

    public void addBook(Book book) {
        books.add(book);
    }

    @Override
    public Iterator<Book> createIterator() {
        return new BookShelfIterator(this);
    }

    // 提供访问 books 的方法给迭代器
    public Book getBookAt(int index) {
        return books.get(index);
    }

    public int getSize() {
        return books.size();
    }
}

// 具体迭代器类
public class BookShelfIterator implements Iterator<Book> {
    private BookShelf bookShelf;
    private int index;

    public BookShelfIterator(BookShelf bookShelf) {
        this.bookShelf = bookShelf;
        this.index = 0;
    }

    @Override
    public boolean hasNext() {
        return index < bookShelf.getSize();
    }

    @Override
    public Book next() {
        if (hasNext()) {
            return bookShelf.getBookAt(index++);
        }
        return null;
    }
}

// 书籍类
public class Book {
    private String title;

    public Book(String title) {
        this.title = title;
    }

    public String getTitle() {
        return title;
    }
}

// 客户端代码
public class Client {
    public static void main(String[] args) {
        // 创建书架并添加书籍
        BookShelf bookShelf = new BookShelf();
        bookShelf.addBook(new Book("Design Patterns"));
        bookShelf.addBook(new Book("Java Programming"));
        bookShelf.addBook(new Book("Algorithms"));

        // 获取迭代器
        Iterator<Book> iterator = bookShelf.createIterator();

        // 遍历书籍
        while (iterator.hasNext()) {
            Book book = iterator.next();
            System.out.println("Book: " + book.getTitle());
        }
        // 输出:
        // Book: Design Patterns
        // Book: Java Programming
        // Book: Algorithms
    }
}

```



# 状态模式

运行一个对象在状态(也就是在成员属性)变化时动态的改变他的行为，看起来就像是修改了他的类,其组成如下：
- Context
- State
- ConcreteState

具体工作方式如下：

![](./assets/State.png)

环境类就是拥有状态的角色，可以在环境类中调用不同的状态的行为，或者切换状态；将不同状态对应的不同行为封装在专门的状态类对象中，使得环境类对象在其内部改变状态时也可以改变自己的行为；

### Analyse

- **优点**：
    1. 封装了转换规则
    2. 可以方便的新增新的状态和状态中的新的行为
    3. 允许状态转换逻辑和状态和成一体，而不是一个巨大的ifelse
    4. 多个对象可以共享一个状态对象
- **缺点**：
    1. 增加系统中类的数量,增加系统复杂度
    2. 对OCP支持不太好，因为如果新增一个状态，就要修改某些状态中的状态转换逻辑函数

1. 简单状态模式：无法切换状态，状态之间相对独立，在环境类中手动指定具体状态，并针对抽象状态编程，符合OCP
2. 可切换状态的状态模式；一般在状态类中，需要引用环境类的SetState来切换状态，不符合OCP

# 命令模式

完全解耦请求的发送者和接受者，二者完全没有引用关系，发送者只需要知道如何发送请求；

**State**： 完全分离请求者和接受者，引入抽象命令接口，并且发送者针对抽象命令接口编程，包含一下部分：
- Command
- ConcreteCommand
- Invoker
- Receiver
- client

具体流程为，首先接受者内部有一系列行为，并有一系列具体命令，具体命令类中包含了Receiver对象，不同的命令调用接受者不同的行为；而发送者只需要包含具体的Command然后调用Command的execute方法即可；例如，在client中，先创建一系列接受者对象，创建具体的想要执行的命令，将命令要作用的对象赋给命令，随后将命令赋发送者，发送者调用execute即可执行命令；

### Analyse

- **优点**：
    1. 降低系统耦合度
    2. 新命令可以很容易的加入到系统中
    3. 可以很方便的设定命令队列和组合命令(即宏命令，其中包含一个命令对象，这个命令对象是宏命令/普通命令，发送一个宏命令会执行多个具体命令)
    4. 可以方便的实现命令的Undo和Redo
- **缺点**：
    1. 可能使得有过多的具体命令类，增加系统的复杂度
